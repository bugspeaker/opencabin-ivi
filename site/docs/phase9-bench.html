#9단계 Test Bench 확장: REST API, 원격 전원, 가상 CAN, 요구사항 추적

2026-11-18에 정리했습니다. 벤치를 사람 없이 돌리려면 다른 도구가 HTTP로 기기와 신호를 다루고, 전원을 껐다 켜고, 차량 네트워크 신호를 받을 수 있어야 합니다. 이 세 가지를 PC 안의 모의 환경으로 만들고, 요구사항과 테스트를 잇는 추적표를 더했습니다.

실제 ECU나 CAN 장비, 전원 공급기, 기능 안전 인증 경험은 없습니다. 이번 단계는 PC 안의 모의 환경과, 개념을 이 프로젝트에 적용해 본 결과입니다. 그래서 첫 화면 목차에서도 'CAN만 모의', '모의 장비', '개념 적용'으로 따로 표시했습니다.

#1. Test Bench REST API (ivi/bench_api.py)

벤치에 붙은 기기를 HTTP로 다루는 API입니다. 다른 팀의 도구나 CI가 adb 명령을 몰라도 기기 상태를 보고, 차량 신호를 넣고, 전원을 껐다 켜고, 테스트를 돌리고, 결과를 가져갈 수 있게 하려고 만들었습니다. 의존성을 늘리지 않으려고 표준 라이브러리(http.server)만 썼습니다.

경로 하는 일
GET /api/devices 벤치에 붙은 기기 목록
GET /api/devices/{serial}/signals 차량 신호 12종, 좌석 온도, 주행 중 제한 여부
POST /api/devices/{serial}/signals 신호 넣기. 예: {"gear": "D", "speed_kmh": 50, "range_km": 25}
GET, POST /api/devices/{serial}/power 전원 상태 보기, 끄기, 켜기, 껐다 켜기
GET /api/runs, GET /api/runs/{name} 최근 실행 요약과 실행 하나의 전체 결과
POST /api/jobs, GET /api/jobs/{id} 기기와 마커를 골라 테스트 실행을 시작하고 상태를 봅니다.

넣는 값은 먼저 검사합니다. 모르는 신호 이름, 범위를 벗어난 값(풍량 9, 온도 35°C), 0.5 단위가 아닌 온도, D가 아닌 기어에서의 속도는 400으로 거절하고 차량에는 넣지 않습니다. 없는 기기는 404, 전원 제어가 없는 기기는 501, 기기 쪽 오류는 502로 돌려줍니다. 테스트가 도는 기기에 신호나 전원 변경이 오면 409로 거절합니다(9절).

벤치 PC 안에서만 쓰도록 기본 주소를 127.0.0.1로 두었습니다. 인증이 없어서 밖으로 열면 안 됩니다.

.venv\Scripts\python tools\bench_api.py
curl http://127.0.0.1:8770/api/devices
curl -X POST http://127.0.0.1:8770/api/devices/emulator-5554/signals -d "{\"gear\": \"D\", \"speed_kmh\": 50}"

#2. 원격 전원 제어 (ivi/power.py)

실제 벤치에서는 헤드 유닛 전원을 프로그래머블 전원 공급기나 스마트 릴레이로 끊고 다시 넣습니다. 그런 장비가 없어서 같은 인터페이스(PowerController) 아래에 구현을 세 가지 두었습니다.

구현 하는 일 확인 방법
EmulatorPower AAOS 에뮬레이터 프로세스를 끄고(adb emu kill) 같은 AVD, 같은 포트, -writable-system으로 다시 켭니다. 실제 에뮬레이터로 E2E
AdbRebootPower 실기기를 adb로 재부팅합니다. 끄기만 되고 원격으로 켜지는 못합니다. 단위 테스트
HttpRelayPower HTTP로 켜고 끄는 스마트 릴레이(Tasmota 형식)입니다. 실제 벤치에 붙일 자리입니다. 가짜 릴레이 서버로 단위 테스트

test_power_cycle_brings_back_app_and_cabin_defaults는 에뮬레이터 전원을 껐다 켠 뒤 세 가지를 봅니다. 3분 안에 부팅이 끝나는지, 앱이 다시 CarService에 붙는지, 공조가 기본값 22.0°C로 시작하는지입니다. 마지막 것은 7단계에서 넣은 VHAL 초기값 덮어쓰기가 재부팅 뒤에도 살아 있는지를 확인하는 것입니다. 부팅에 걸린 시간은 단독으로 돌렸을 때 24.3초, 전체 실행의 마지막에 돌렸을 때 32.2초였습니다.

전원을 껐다 켜면 Appium 세션이 끊깁니다. 그래서 conftest가 이 테스트를 실행 순서의 맨 끝으로 보내고, 테스트 안에서 새 세션을 만들어 화면을 확인합니다.

#3. 가상 CAN 버스와 게이트웨이 (ivi/can_gateway.py)

실제 차에서는 VCU, BMS, BCM 같은 ECU가 CAN으로 신호를 보내고, 차량 쪽 서비스가 그 값을 VHAL property로 올려 줍니다. 이 자리를 PC 안의 가상 ECU와 가상 CAN 버스로 채웠습니다.

flowchart LR
    E[시험용 ECU<br>VCU, BMS, BCM] -->|CAN 프레임| B((가상 CAN 버스))
    B --> G[게이트웨이]
    G -->|adb, VHAL| V[VHAL / Mock]
    V --> A[IVI 앱 화면]
    A -->|공조 조작| V
    G -->|IVI_HvacStatus| B
  • 프레임과 신호는 DBC 파일(ivi-tests/dbc/opencabin.dbc)에 정의했고, cantools로 인코딩하고 풉니다. 속도는 0.01 km/h 단위, 외기 온도는 0.5°C 단위에 -40 오프셋처럼 실제 DBC와 같은 방식으로 적었습니다.
  • 버스는 python-can의 virtual 인터페이스입니다. 같은 프로세스 안의 여러 노드가 같은 채널을 씁니다.
  • 받는 쪽: VCU의 속도와 기어, BMS의 배터리와 주행 가능 거리, BCM의 도어와 외기 온도를 풀어서 차량 어댑터에 넣습니다. ECU는 같은 값을 100~500 ms마다 계속 보내기 때문에, 값이 바뀐 프레임만 넣어 adb 왕복을 줄였습니다. 차량 쪽이 느리면 상태 신호는 최신 값으로 합치고, 기어와 도어는 순서대로 넣습니다(9절).
  • 보내는 쪽: 공조 상태(좌석 온도, A/C, 최대 냉방, AUTO, 풍량)를 읽어 IVI_HvacStatus 프레임을 1초마다 보냅니다.
테스트 확인하는 것
test_can_drive_frames_reach_screen VCU 프레임으로 D, 50 km/h를 보내면 화면 속도와 주행 제한 배지가 바뀌고, P로 바꾸면 돌아옵니다. 같은 프레임이 계속 와도 VHAL에는 한 번만 넣습니다.
test_can_battery_and_door_frames_reach_screen BMS의 주행 가능 거리 25 km에 '충전 필요'가 뜨고, BCM의 문 열림에 도어 표시가 '열림'이 됩니다.
test_climate_button_goes_out_on_can 화면에서 운전석 온도를 올리면 버스에 나가는 IVI_HvacStatus의 운전석 온도가 22.5°C가 됩니다.

게이트웨이는 차량 어댑터를 거치기 때문에 같은 테스트가 AAOS(VHAL)와 태블릿(Mock)에서 모두 돕니다.

다루지 못한 것도 분명합니다. 실제 ECU, CAN 트랜시버, 버스 부하와 오류 프레임, 타이밍은 보지 않았습니다. Ethernet, DDS, SOME/IP도 해 보지 않았습니다.

#4. 요구사항 추적표와 후방 카메라 2초

#요구사항과 테스트를 양쪽으로 잇기

요구사항 26개에 ID를 붙이고, 모든 테스트 함수에 @pytest.mark.req("ID")를 달았습니다. tools/trace_report.py가 둘을 이어 요구사항 추적표를 만듭니다. 요구사항마다 확인하는 테스트와 기기별 최신 결과가 나오고, 반대로 테스트 파일마다 어떤 요구사항을 확인하는지도 나옵니다.

프레임워크 단위 테스트 test_every_requirement_has_a_test_and_every_test_a_requirement가 CI에서 세 가지를 막습니다. 테스트가 없는 요구사항, 요구사항이 없는 테스트, 없는 ID를 가리키는 테스트입니다. A-SPICE가 요구하는 요구사항–시험 양방향 추적을 개인 프로젝트 규모로 적용해 본 것이고, 표준 심사를 받은 것은 아닙니다.

#후방 카메라가 2초 안에 뜨는지

미국 기준 FMVSS 111은 후진을 시작하고 2.0초 안에 후방 영상을 보여 주라고 정해 두었습니다. test_rear_camera_appears_within_two_seconds는 기어를 R로 바꾼 순간부터 카메라 화면이 보일 때까지를 다섯 번 재고, 가장 느린 값으로 판정합니다. 신호를 넣는 adb 시간까지 포함한 값이라 실제보다 느리게 잡힙니다. 법규의 2초 기준을 빌려 온 시험이고, 재는 것은 앱의 후방 카메라 화면 요소가 나타날 때까지입니다. 실제 카메라 영상이나 실차에서 잰 값은 아닙니다.

#7. 외부 검토 반영 (2026-11-19)

공고 기준 외부 검토에서 '문서에는 있는데 코드에는 없는 것'을 짚어 받았습니다. 그 가운데 코드로 고칠 수 있는 것을 고쳤습니다.

지적 고친 것
Release 게이트 다섯 조건 가운데 2, 3, 5는 검사하는 코드가 없었습니다. tools/release_gate.py가 실행 결과 파일로 다섯 조건을 모두 확인하고, 어기면 종료 코드 1로 끝나게 했습니다. 격리 목록은 사유, 등록일, 해제 조건 칸이 빠진 줄을 거절합니다. 알려진 결함 목록 known_defects.txt를 두었고, ivi-ci.yml의 Release 후보 실행 뒤에 붙였습니다. 단위 테스트는 게이트 16개, 격리 목록 형식 5개입니다.
'고정 sleep은 쓰지 않습니다'라고 썼는데 3곳에 있었고, wait_value는 2곳에만 적용돼 있었습니다. sleep 3곳을 stays(정한 시간 동안 계속 읽어 한 번이라도 바뀌면 실패)로, 값 대기 47곳을 wait_value로 바꿨습니다.
테스트마다 logcat -c로 버퍼를 지웠습니다(같은 기기를 쓰는 다른 도구의 로그까지 지웁니다). 테스트 시작 시각을 찍어 두고, 실패 때 logcat -T로 그 뒤만 모으게 했습니다.
반복 실행 원자료가 저장소에 없었습니다. --repeat이면 JUnit 파일이 회차마다 덮어써졌습니다. 5회 × 2기기 결과 파일 10개를 evidence에 남기고, JUnit 이름에 run id를 넣었습니다. 다시 세 보니 반복 실행 통계의 flaky_report 출력 절이 r5 뒤의 다른 실행을 섞어 센 것이어서(1,250건, flaky 0, 실패 0은 그대로) 원자료 기준으로 다시 만들었습니다.
범위 밖 온도 테스트가 '값 A 또는 끝값'처럼 넓게 판정했습니다. 기기마다 기대값을 하나로 정했습니다(AAOS 15.5 → 16.0, Mock 16.0 → 16.5).
태블릿 숫자가 VHAL 경로까지 증명하는 것처럼 읽혔습니다. 숫자 옆에 '차량 값은 앱 안 Mock'과 기기별 건수(AAOS 640, 태블릿 610)를 적었습니다.

프레임워크 단위 테스트는 71개에서 94개가 됐습니다.

바꾼 테스트 코드로 두 기기 전체를 1회 다시 돌렸습니다(원자료). 위 6절의 결과 표와 반복 실행 5회는 바꾸기 전 코드 기준입니다.

같은 기기의 실행 요청 두 개가 동시에 오면 '실행 중인지 보기'를 둘 다 통과해 둘 다 시작했습니다. 테스트가 도는 기기에도 신호 넣기와 전원 끄기가 들어갔습니다. 기기마다 점유를 두고, 보기와 등록을 한 잠금 안에서 합니다. 동시에 온 요청 8개 가운데 1개만 받고 7개는 409로 거절합니다. 테스트가 도는 동안 그 기기의 신호·전원 변경은 409로 거절하고, 읽기와 다른 기기는 그대로 됩니다. 전원을 껐다 켜는 중에 온 실행 요청은 끝난 뒤에 시작합니다.
실행 파일이나 작업 폴더가 없으면 작업 스레드만 끝나고 상태가 'running'에 남아, 그 기기에서 다시 실행할 수 없었습니다. 끝나지 않는 실행에는 시간 제한이 없었습니다. 시작하지 못하면 error로 남깁니다. 시간 제한(기본 3600초, --job-timeout)을 넘으면 프로세스를 멈추고 timeout으로 남깁니다. 어느 길로 끝나든 점유를 풉니다. 출력은 파이프 대신 임시 파일로 받아, 테스트가 띄운 프로세스가 출력을 물고 있어도 기다리지 않습니다.
차량 쓰기가 느리면 받는 스레드가 막혀 CAN 프레임이 쌓였습니다. 차량 쓰기 40 ms에 속도가 다른 프레임 50개를 5 ms 간격으로 보내면, 50번을 차례로 써서 버스에 43개가 쌓이고 마지막 값이 들어가기까지 약 1,750 ms가 걸렸습니다. 받기와 넣기를 스레드로 나눴습니다. 속도, 배터리처럼 지금 값만 의미 있는 신호는 최신 값으로 합칩니다. 기어, 도어처럼 바뀐 사실이 사건인 신호는 합치지 않고 순서대로 넣습니다(R을 건너뛰면 후방 카메라가 뜨지 않습니다). 같은 조건에서 차량 쓰기는 8번, 쌓인 프레임은 0개, 지연은 약 50 ms였습니다(3회 같음). 합친 수, 버린 수, 지연은 diagnostics()로 보고, E2E 정리 단계에서 출력합니다.
stop()이 스레드를 5초 기다린 뒤 멈췄는지 보지 않고 돌아와, 멈춘 줄 안 게이트웨이가 다음 테스트의 차량을 바꿀 수 있었습니다. 시간 안에 못 멈추면 GatewayStopTimeout을 내고, 그동안 다시 시작하지 못하게 했습니다. 멈추라고 한 뒤에는 대기 중인 프레임을 버리고 차량에 넣지 않습니다.
같은 게이트웨이를 다시 시작해도 마지막으로 넣은 값을 기억해, 멈춘 사이 차량이 초기화됐으면 첫 프레임을 넣지 않았습니다. 시작할 때 그 기록을 비웁니다. 켜져 있는 동안 같은 값을 거르는 것은 그대로입니다.
(다시 읽어 찾은 것) serial에 목록을 보내거나 신호에 NaN, Infinity를 보내면 서버 오류(502)가 났습니다. Content-Length가 음수면 연결이 닫힐 때까지 요청 스레드가 묶였습니다. 모두 400으로 바로 답하고, 64 KB가 넘는 본문은 읽지 않고 413으로 답합니다.
(다시 읽어 찾은 것) 아직 쓰는 중인 결과 파일 하나 때문에 /api/runs 전체가 실패했습니다. 그 줄만 오류로 표시합니다. 그 파일을 직접 달라고 하면 503으로 답합니다.
(다시 읽어 찾은 것) CAN 버스 읽기에서 예외가 나면 받는 스레드가 기록 없이 끝났습니다. 전원 제어의 adb devices에는 시간 제한이 없어, adb 서버가 멈추면 껐다 켜기가 제한 시간을 지키지 못하고 기기를 계속 붙잡았습니다. 버스 오류는 남기고 계속 받습니다. 오류와 적용 기록은 최근 500개까지 둡니다. adb devices에 10초 제한을 두었습니다.
(다시 읽어 찾은 것) 자식 pytest를 띄우는 다섯 곳이 Python 3.12 Windows에서 한글을 cp949로 받아 utf-8로 읽다 깨졌습니다. 검토 환경에서는 단위 테스트 1개가 실패했습니다. 자식 프로세스에 PYTHONIOENCODING=utf-8을 줍니다. CI도 3.12입니다.

검토가 '확정하지 못함'으로 남긴 앱의 강제 형변환(value as Float 등)은 고치지 않았습니다. 값이 STATUS_AVAILABLE인지 먼저 보고, 값의 형은 표준 VHAL property 정의로 정해져 있기 때문입니다.

프레임워크 단위 테스트는 204개에서 223개가 됐습니다. 시간에 기대는 테스트(동시 요청, 느린 차량, 멈추지 않는 호출)는 8번 반복해 모두 통과했습니다.

#동시 조작 E2E

차 안에서는 음악을 틀어 둔 채 공조를 바꾸고, 안내를 받으며 통화합니다. 기능별 테스트는 그 기능만 봐서, 뒤에서 도는 기능이 다른 조작 뒤에도 그대로인지는 확인한 적이 없었습니다. 요구사항 SYS-02를 더하고 tests/test_concurrency.py에 테스트 5개(매개변수 조합까지 6개)를 넣었습니다.

테스트 확인하는 것
test_music_keeps_playing_while_climate_is_operated 음악 재생 중 공조 화면에서 두 좌석 온도, 풍량, A/C를 바꾸면 값은 모두 차량에 들어가고 같은 곡이 재생 중입니다. 음악 화면을 보는 동안 차량 쪽 온도가 바뀌어도 1.5초 동안 그대로입니다.
test_guidance_and_music_continue_while_temperature_changes_on_the_move 경로 안내와 음악 중에 120 km/h로 달리며 아래 바로 온도를 바꾸면, 온도는 차량에 들어가고 안내는 같은 목적지로 계속 줄고 음악은 재생 중입니다.
test_climate_works_during_call_and_music_resumes_after 통화 중에 공조를 바꾸면 차량에 들어가고, 통화 시간은 계속 흐르고, 음악은 '통화 중'입니다. 끊으면 같은 곡이 다시 나오고 공조 값은 그대로입니다.
test_screen_and_vehicle_changes_at_once_end_in_same_value 화면에서 +를 세 번 누르는 동안 다른 스레드가 차량 쪽 온도를 세 번 바꿉니다. 어느 쪽이 마지막이든 화면과 차량 신호가 같은 값으로 끝나고, 조수석은 그대로입니다.
test_quick_taps_are_all_applied (좌석 2) 사람이 빠르게 누르는 간격(0.1초)으로 +를 네 번 누르면 네 번 모두 들어가 24.0°C가 됩니다. 앱은 차량에서 돌아온 값에 0.5를 더해 쓰므로, 값이 돌아오기 전에 다음 누름이 오면 누른 것이 사라질 수 있어 넣었습니다.

AAOS 에뮬레이터, 화웨이 태블릿, 갤럭시 폴드에서 이 6개와 바꾼 게이트웨이를 쓰는 CAN E2E 3개가 모두 통과했습니다. 빠른 누름은 간격을 0(누름 하나에 에뮬레이터 1520 ms, 태블릿 약 100 ms)까지 줄여도 두 기기 모두 네 번이 다 들어갔습니다. 에뮬레이터의 VHAL 왕복이 그보다 빨라서로 보이고, VHAL 왕복이 느린 실제 차량에서는 다를 수 있습니다. CAN 프레임을 받아 차량에 다 넣기까지는 AAOS 54107 ms, 태블릿 96106 ms, 폴드 92176 ms였고, 합치거나 버린 프레임은 없었습니다.

빠른 누름은 처음에 Appium W3C 동작으로 보냈습니다. AAOS 에뮬레이터에서는 누른 채 기다리는 동안 UiAutomator2가 만드는 MOVE 이벤트 주입이 실패해, 동작 전체가 실패했습니다. 앱이 아니라 도구 문제여서 adb 셸 한 번에 input tap을 잇는 방식으로 바꿨습니다.

이 6개는 아직 두 기기 × 3회 반복에 들어가지 않았습니다.

주요 업무, 자격요건, 우대사항마다 이 프로젝트에서 한 일과 근거입니다.
항목을 누르면 근거가 되는 테스트 결과나 기록으로 이동합니다.
모의 환경에서만 해 본 항목은 오른쪽에 따로 표시했습니다.

주요 업무 7개

  1. 01 IVI 서비스별·단계별 검증 전략HVAC, 차량 설정(도어), 주행 정보 패널(앱 왼쪽, 계기판 역할), 미디어를 나누고, 서비스마다 주요 위험과 확인 방향(화면→신호, 신호→화면)을 정해 테스트했습니다. 단계는 앱 단위 테스트, 프레임워크 단위 테스트, 에뮬레이터·태블릿 E2E까지이고 HIL과 실차는 하지 않았습니다. 클러스터 제외서비스별·단계별 표
  2. 02 Smoke · Sanity · Regression 게이팅smoke 13개, sanity 25개, regression 106개를 고르는 기준, 시간, 통과 조건을 정하고 PR, main, Nightly, Release마다 돌리는 범위를 나눴습니다. 게이트 기준 표
  3. 03 UI와 CarProperty/VHAL을 잇는 E2E화면 조작이 차량 신호로, 신호 변화가 화면으로 이어지는지 양쪽을 봤습니다. 좌석과 문은 area마다 확인합니다. 테스트 31개
  4. 04 터치부터 하위 연동까지 통합 검증AAOS 에뮬레이터에서 화면의 운전석 온도를 한 칸 올리면, 앱 → CarService → VHAL로 바뀐 값을 게이트웨이가 adb로 읽어 CAN 프레임(IVI_HvacStatus)으로 내보내고, 그 값이 22.5°C인지 확인합니다. 반대로 가상 ECU가 보낸 CAN 프레임이 VHAL을 거쳐 화면에 보이는지도 봅니다. 테스트 13개
  5. 05 프레임워크와 스크립트 유지보수7단계에서 아래 바 구성이 바뀌었을 때 화면 객체(screens.py)의 여는 경로만 고쳤고, 화면 개편 때문에 바꾼 테스트는 기존 64개 가운데 1개입니다. 7단계 기록
  6. 06 ADB · shell · CarPropertyManager로 Property Injection과 이벤트 검증앱과 같은 경로가 필요한 설정 온도는 cmd car_service로, 속도·기어 같은 읽기 전용 값과 차량 쪽에서 바뀐 공조·도어 값은 dumpsys로 VHAL에 바로 넣습니다. 이벤트는 값을 넣은 뒤 앱 화면이 바뀌는 것으로 확인합니다(앱이 onChangeEvent로 받은 값). 이벤트 횟수, 순서, 시각, onErrorEvent는 따로 판정하지 않습니다. 테스트 38개
  7. 07 Flaky 최소화 · 병렬 실행두 기기를 병렬로 3번 반복해 테스트 873건을 돌렸고, 재시도로 통과한 것(flaky)은 0건입니다. 재시도 기록, 격리 목록, flaky 통계와 Release 게이트를 만들었습니다. 반복 실행 통계

자격요건 6개

  2. 09 Android/AAOS 테스트 자동화 구축과 운영AAOS 에뮬레이터와 태블릿에서 E2E 150개를 돌리고, 테스트마다 판정 직후 화면을 남겼습니다. 테스트 150개
  3. 10 Python 테스트 프레임워크 (pytest)훅, 픽스처, 마커와 결과 기록 플러그인을 만들었습니다. 프레임워크 단위 테스트가 233개 있습니다. 3단계 기록
  4. 11 Appium 등 UI 자동화 도구Appium(UiAutomator2)을 AAOS의 다중 사용자 환경(user 10)에 붙여 썼습니다. 1단계 기록
  5. 12 ADB · Logcat · Shell테스트 도중 앱 크래시나 ANR이 logcat에 남으면 화면 판정이 통과해도 실패로 합니다. 실패하면 logcat을 자동으로 저장하고, 앱이 강제로 꺼지던 원인도 logcat에서 찾았습니다. 결함 기록
  6. 13 Git · CI/CDPR 단위로 작업했고, GitHub Actions가 PR마다 빌드, 단위 테스트, 호스트 러너의 AAOS 에뮬레이터 smoke 13개를 무인으로 돌립니다. 태블릿과 전체 회귀는 작업 PC에서 돌렸습니다. 실행 기록

우대사항 4개

  1. 14 VHAL · CarService · CarPropertyManager신호 12종을 연결하면서 area 구성, 권한 등급, priv-app 허용 목록을 다뤘습니다. 테스트 38개

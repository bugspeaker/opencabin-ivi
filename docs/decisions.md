# 결정 기록

이 프로젝트에서 방향을 정한 결정마다 상황, 고른 것, 버린 것, 근거, 결과를 적었습니다. 근거는 단계별 기록에 남은 측정값이고, 각 항목에서 그 기록으로 이어집니다.

코드는 거의 전부 AI 코딩 도구(Claude Code)가 작성했습니다. 아래 결정도 모두 Claude가 제안했고, 제가 확인해 채택 여부를 확정했습니다('누가' 열, [만든 사람과 만든 방식](portfolio.md#만든-사람과-만든-방식)). 이 문서는 무엇을 왜 골랐는지를 남기기 위한 것입니다.

## 1. 기기를 AAOS 에뮬레이터와 일반 태블릿 두 종류로

- **상황**: 실제 차나 AAOS 실기기가 없습니다. 에뮬레이터만 쓰면 CarService와 VHAL 경로는 볼 수 있지만 실기기에서만 나는 문제는 보이지 않습니다.
- **고른 것**: 같은 테스트 코드를 AAOS 에뮬레이터(CarService와 에뮬레이터 VHAL)와 화웨이 태블릿(앱 안 Mock 차량)에서 돌립니다. 기기 차이는 차량 어댑터와 `Device` 안에서 처리합니다.
- **버린 것**: 에뮬레이터 하나만 쓰는 방법. 태블릿 전용 테스트를 따로 두는 방법.
- **근거**: 원인을 찾는 데 가장 오래 걸린 두 건(탭 한 번 10초, 21번째 테스트에서 앱이 사라짐)이 모두 태블릿에서 나왔습니다([포트폴리오 3장](portfolio.md#3-결함과-원인-분석)).
- **결과**: 129개 가운데 AAOS 전용 7개와 태블릿 전용 1개(12시간 시계)를 뺀 121개가 두 기기에서 같은 코드로 돕니다.

## 2. 화웨이 태블릿에서는 누르기만 adb로

- **상황**: 태블릿에서 탭 한 번에 10초가 걸렸습니다.
- **고른 것**: 요소는 Appium으로 찾고, 누르는 것만 `adb shell input tap`으로 요소 중심을 누릅니다. 환경 변수 `IVI_TAP`으로 바꿀 수 있습니다.
- **버린 것**: Appium 대기 설정(`waitForIdleTimeout`, `actionAcknowledgmentTimeout`)을 0으로 바꾸는 방법, `mobile: clickGesture`, W3C actions. 모두 10초 그대로였습니다.
- **근거**: `element.click()` 10,377 ms, `clickGesture` 10,099 ms, W3C actions 10,430 ms, `adb shell input tap` 117 ms. adb 왕복은 65 ms라 원인이 아니었습니다([phase3](phase3-framework.md)).
- **결과**: 태블릿 전체 실행이 7분 22초에서 1분 32초로 줄었습니다(당시 31개). 화면 객체와 테스트 코드는 바꾸지 않았습니다.

## 3. `inject-vhal-event`는 쓰지 않음

- **상황**: 속도, 기어 같은 읽기 전용 센서 값을 테스트가 바꿔야 합니다.
- **고른 것**: `dumpsys <VHAL> --set`(root)으로 VHAL에 값을 넣습니다.
- **버린 것**: `cmd car_service inject-vhal-event`.
- **근거**: `inject-vhal-event`는 이벤트만 보내고 저장된 값은 그대로라, `get-property-value`로 넣은 값을 확인할 수 없었습니다([phase1](phase1-spike.md)).
- **결과**: 넣은 값을 같은 경로로 다시 읽어 판정할 수 있습니다.

## 4. 값을 넣는 길을 둘로 나눔

- **상황**: 테스트가 차량 값을 준비하는 방법이 두 가지 있습니다. CarService를 거치는 `cmd car_service set-property-value`와 VHAL에 바로 넣는 `dumpsys VHAL --set`입니다.
- **고른 것**: 앱이 바꾸는 값(운전석, 조수석 설정 온도)은 앱과 같은 CarService 경로로 준비합니다. 차량(ECU) 쪽에서 바뀌는 값(속도, 기어, 그리고 A/C, 풍량, 도어의 '차량 쪽 변화')은 VHAL에 바로 넣습니다. 읽기는 모두 CarService로 합니다.
- **버린 것**: 모든 값을 한 경로로 넣는 방법.
- **근거**: 2026-11-18에 에뮬레이터에서 확인했습니다. `set-property-value`로 15.5°C를 넣으면 `IllegalArgumentException`으로 거절되고, `dumpsys VHAL --set`은 받습니다. 차량 쪽에서 이상한 값이 올라오는 상황은 VHAL에 바로 넣어야 만들 수 있습니다. 16.0~28.0°C 범위는 이 프로젝트가 에뮬레이터 VHAL 설정 덮어쓰기(`ivi-app/privileged/vhaloverride/opencabin.json`)의 `minFloatValue`, `maxFloatValue`로 정한 값이고, 이 설정으로 띄운 에뮬레이터에서 범위 밖 값이 거절됐습니다.
- **결과**: 이 구분으로 경계값 테스트를 만들었고, 앱 결함 1건을 찾았습니다([포트폴리오 3장 8번](portfolio.md#3-결함과-원인-분석)).

## 5. 기준 값 31개를 adb 한 번에 묶고 응답 수를 셈

- **상황**: 차량 신호는 앱을 다시 띄워도 남아서, 테스트마다 12종을 기준 값으로 되돌려야 합니다. AAOS에서는 area를 곱하면 `--set`이 31번입니다.
- **고른 것**: 31개 명령을 adb shell 한 번에 묶어 보내고, 성공 응답(`Set property`)이 31개인지 셉니다. 모자라면 통째로 한 번 더 보내고 그 사실을 기록합니다.
- **버린 것**: 하나씩 보내는 방법(왕복 31번). 응답을 세지 않고 보내기만 하는 방법.
- **근거**: 8단계 기준(당시 신호 11개, 26번)으로 테스트가 84개에서 108개로 늘었는데 테스트당 시간은 4.1초에서 3.7초로 줄었습니다([phase8](phase8-signals.md)).
- **결과**: 주입 누락이 있으면 그 테스트의 준비 단계에서 바로 드러납니다.

## 6. 앱 프로세스 종료는 세션 시작 때 한 번만

- **상황**: 태블릿에서 실행할 때마다 21번째 테스트에서 앱이 사라졌습니다.
- **고른 것**: 프로세스 종료는 세션 시작 때 한 번만 하고, 테스트마다는 `--activity-clear-task`로 화면만 초기화합니다. 그래도 앱이 없으면 한 번 더 띄우고 `app_relaunch`로 기록합니다.
- **버린 것**: 테스트마다 `am start -S`로 프로세스를 새로 띄우는 방법.
- **근거**: 실패 자료의 logcat에 `Force stopping dev.opencabin.ivi … iAwareF[CrashClean]`이 있었습니다. 화웨이 OS가 반복 재시작을 크래시로 본 것입니다([phase4](phase4-operations.md)).
- **결과**: 바꾼 뒤 3회 연속 실행에서 앱 재실행 0회였습니다.

## 7. 플랫폼 결함은 `xfail(strict=True)`

- **상황**: AAOS 에뮬레이터 기본 SystemUI(1024×768)에서 운전석 온도 ▲가 홈 버튼과 72×76px 겹쳐 눌리지 않습니다. 앱이 아니라 플랫폼 쪽 문제입니다.
- **고른 것**: 테스트를 남기고 `xfail(strict=True)`로 걸었습니다.
- **버린 것**: 테스트를 지우거나 skip하는 방법. 좌표를 옮겨 누르는 우회.
- **근거**: strict이면 결함이 고쳐졌을 때 XPASS가 실패로 바뀌어 바로 알 수 있습니다. skip은 고쳐져도 알려 주지 않습니다.
- **결과**: 실행마다 '알려진 결함 1'로 남고, Release 게이트(`tools/release_gate.py`)가 xfailed가 된 테스트를 결함 목록(`ivi-tests/known_defects.txt`)과 비교합니다.

## 8. 재시도는 1회, 재시도로 통과하면 flaky로 따로 기록

- **상황**: 기기 테스트는 가끔 흔들립니다. 재시도를 하지 않으면 한 번 흔들린 것으로 게이트가 막히고, 재시도를 통과로 치면 흔들림이 보이지 않습니다.
- **고른 것**: `--reruns 1 --reruns-delay 2`. 재시도에서 통과한 것은 passed가 아니라 flaky로 기록하고, 첫 실패의 자료를 남깁니다.
- **버린 것**: 재시도 없음, 재시도 여러 번, 재시도 통과를 passed로 치는 방법.
- **근거**: 4단계에서 일부러 첫 시도만 실패하는 테스트를 만들어 `flaky, reruns 1`로 기록되고 첫 실패 자료가 남는 것을 확인했습니다([phase4](phase4-operations.md)).
- **결과**: 2026-11-18 반복 실행 5회에서 flaky 0건([반복 실행 통계](flaky-report.md)).

## 9. 격리는 후보만 내고 사람이 정함

- **상황**: 흔들리는 테스트를 게이트에서 빼야 할 때가 있지만, 자동으로 빼면 진짜 결함이 숨을 수 있습니다.
- **고른 것**: 불안정률 10% 이상이고 5회 이상 실행된 테스트를 격리 후보로, 격리 중 20회 연속 통과한 테스트를 해제 후보로 냅니다. 격리 목록에는 사유, 등록일, 해제 조건을 꼭 적고(칸이 빠지면 목록을 읽을 때 실패), 격리한 테스트도 계속 돌려 결과를 남깁니다.
- **버린 것**: 후보를 자동으로 격리하는 방법.
- **근거**: 격리가 게이트를 우회하는 통로가 되지 않게 하려는 것입니다. Release 게이트(`tools/release_gate.py`)는 격리가 2개를 넘으면 막습니다([포트폴리오 4-1](portfolio.md#4-1-게이트-단계와-기준)).
- **결과**: 지금 격리 목록은 비어 있습니다.

## 10. sanity를 대표 경로로 줄임

- **상황**: sanity가 55개(전체 123개의 45%)로 regression(49개)만큼 커져서, '빠른 확인'이라는 뜻이 흐려졌습니다.
- **고른 것**: 서비스마다 '화면→신호', '신호→화면' 대표 경로 하나씩과 주행 중 제한 대표만 sanity에 남겼습니다. 같은 경로를 다른 화면에서 다시 보는 것, 조합, 경계값은 regression으로 내렸습니다.
- **버린 것**: 개수를 그대로 두는 방법.
- **근거**: 2026-11-18 낮 실행의 시간 합으로 main 게이트(smoke + sanity)가 기기당 약 4분 30초~4분 45초였습니다.
- **결과**: sanity 25개, main 게이트 기기당 약 2분 15초([포트폴리오 4-1](portfolio.md#4-1-게이트-단계와-기준)).

## 11. 대기는 다시 볼 예외만 기다림

- **상황**: 조건 대기(`wait_until`)가 모든 예외를 '아직 아님'으로 보고 제한 시간까지 기다렸습니다. 대기 안에서 부른 화면 객체가 또 10초를 기다려 제한 시간이 최대 약 20초로 겹쳤고, 실패 메시지에는 `마지막 값: False`만 남았습니다.
- **고른 것**: 요소가 아직 없음, adb 실패, 숫자로 아직 못 바꾸는 화면 글자처럼 다시 볼 예외만 기다리고, AttributeError, TypeError, KeyError 같은 코드 오류는 바로 올립니다. 대기 안에서 부른 화면 객체는 한 번만 찾습니다. 값을 기다릴 때는 마지막으로 읽은 값을 실패 메시지에 남깁니다(`wait_value`).
- **버린 것**: 모든 예외를 기다리는 방법. 숫자 변환 오류(ValueError)까지 바로 올리는 방법(화면이 바뀌는 중간에 '--'가 보이면 새 flaky가 생김).
- **근거**: 단위 테스트로 오타가 1초 안에 원래 예외로 올라오는 것, 대기 중첩이 없는 것을 확인했습니다(`ivi-tests/unit/test_waits.py`). 이 수정 뒤 경계값 테스트의 실패 메시지는 '마지막으로 읽은 값: 22.8'이 됐습니다.
- **결과**: 수정 뒤의 반복 실행 5회에서 대기 때문에 생긴 실패는 0건입니다.

## 12. 공개 저장소에 개인 PC를 self-hosted 러너로 붙이지 않음

- **상황**: e2e job은 self-hosted Test Bench용으로 작성했지만, 저장소는 지원서 링크용으로 공개했습니다.
- **고른 것**: e2e는 저장소 변수 `IVI_BENCH=online`일 때만 돌게 두고, 지금은 켜지 않았습니다. 워크플로에는 포크 PR이 e2e를 돌리지 못하게 하는 조건과, `workflow_dispatch` 입력을 환경 변수로 넘기는 처리를 넣었습니다.
- **버린 것**: 개인 PC를 이 공개 저장소의 러너로 등록하는 방법.
- **근거**: 공개 저장소의 self-hosted 러너는 다른 사람의 PR 코드를 그 PC에서 실행할 수 있습니다.
- **결과**: e2e는 같은 명령(`run_bench.py`)을 작업 PC에서 실행해 확인했습니다. GitHub에서 e2e를 돌린 기록은 아직 없습니다.

## 13. Appium 세션이 끊기면 다음 테스트 시작 때 다시 붙이고 기록

- **상황**: Appium 세션은 만드는 데 기기당 5~15초가 걸려 실행 전체에서 하나를 씁니다. 2026-11-19 막 켠 AAOS 에뮬레이터에서 UiAutomator2 계측 프로세스가 죽자(`instrumentation process is not running`), 그 세션에 묶인 뒤의 테스트 129개가 모두 준비 단계 오류가 됐습니다. 외부 검토에서도 '무인 Nightly에서 세션 끊김 한 번이 전체 실패로 번진다'고 짚었던 부분입니다.
- **고른 것**: 드라이버 자리에 세션을 감싸는 `SessionHolder`를 두고, 테스트를 시작할 때마다 UiAutomator2 서버까지 가는 가벼운 요청(창 크기)으로 확인합니다. 끊겼으면 닫고 새로 만들며, 서버가 다시 뜨는 중일 수 있어 3초 간격으로 3번까지 해 봅니다. 다시 붙인 일은 `session_restart`로 기록하고 flaky 통계에 '세션 재연결' 열로 보여 줍니다.
- **버린 것**: 테스트마다 세션을 새로 만드는 방법(129개 × 5~15초). 세션 확인 없이 실패한 테스트만 재시도하는 방법(재시도도 같은 죽은 세션을 쓴다). 다시 붙인 일을 기록하지 않는 방법.
- **근거**: 앱 재실행(`app_relaunch`), 신호 재시도(`vhal_retry`)와 같은 원칙입니다. 세션은 자동으로 다시 붙이고, 다시 붙인 횟수를 결과에 남깁니다. 테스트 도중에 끊긴 시도는 실패로 남겨 재시도에서 통과하면 flaky가 되고, Release 게이트(flaky 0 조건, 지금 번호로 조건 3)에서는 막힙니다.
- **결과**: 2026-11-20에 일부러 끊어 확인했습니다. AAOS에서 UiAutomator2 서버를 두 번 강제 종료한 실행과 태블릿에서 Appium 서버를 다시 켠 실행 모두 smoke와 sanity 38개가 통과했고, 세션 재연결은 각각 3번, 1번이었습니다([확인 기록](evidence/2026-11-20-session-recovery/README.md)). AAOS의 3번 가운데 1번은 끊기 전에 계측 프로세스가 스스로 죽은 것이었습니다. 끊지 않고 두 기기 전체 129개를 돌린 실행도 재시도 0, 세션 재연결 0으로 통과했습니다.
